01 — Overview
What is this project?
The big picture in one paragraph

This is an automated browser testing project. It opens Chrome (or Edge), goes to websites like Amazon, Facebook, and BBC, does things like searching for products — then checks that the right things happened. All of this is controlled by TestNG, a tool that decides which tests run, in what order, and how many at once.

The project is organized into three layers:

🏗️

Base layer (base/ folder) — sets up and tears down browsers, reads config, manages reports.
Test layer (tests/ folder) — the actual things you want to verify on websites.
Support layer (listeners/, utils/) — watches what happens and writes a report automatically.

What runs, in what order
Follow this diagram every time you run a test suite

Key idea: @BeforeSuite and @AfterSuite run exactly once per suite run. @BeforeMethod and @AfterMethod run once for every single @Test method — so if you have 10 tests, setup and teardown run 10 times total.

04 — Files Explained
Every file, plain and simple
Read these in order — each one builds on the previous
base/DriverFactory.java
Browser Manager
"Think of it as a numbered locker room — each test thread gets its own locker, so browsers never share or mix up."

What it does: When a test needs a browser, this file creates one. When the test is done, it destroys it. The critical trick: it uses ThreadLocal — a Java tool that gives every running thread its own separate copy of an object. Thread A gets its own Chrome. Thread B gets its own Edge. They never cross.

Where it starts: createDriver(browser, headless) — builds the Chrome/Edge/Firefox with specific options then stores it in the ThreadLocal.

Where it ends: quitDriver() — closes the browser and removes it from the ThreadLocal (so memory isn't wasted).

ThreadLocal<WebDriver> ChromeOptions EdgeOptions EAGER PageLoadStrategy
// ONE WebDriver per thread — never shared private static final ThreadLocal<WebDriver> DRIVER = new ThreadLocal<>(); // Creates browser + stores in this thread's slot public static void createDriver(String browser, boolean headless) { … } // Destroys browser + clears slot public static void quitDriver() { DRIVER.get().quit(); DRIVER.remove(); }
base/BaseClass.java
Parent of All Tests
"Think of it as the school principal — every student (test class) must follow these rules (setup/teardown) automatically."

What it does: Every test class extends BaseClass. That means they all automatically get a browser opened before each test and closed after. You never write that code twice. It also reads parameters from the XML (which browser, which URL, headless or not).

Where it starts: @BeforeSuite loadConfiguration() — runs once. Reads all .properties files. Creates the HTML report.

@BeforeMethod setUp() — runs before every test. Reads browser/url/headless parameters. Creates a browser via DriverFactory. Opens the website.

Where it ends: @AfterMethod tearDown() — runs after every test. Closes the browser. Unloads the report node for this thread.

@BeforeSuite @BeforeMethod @AfterMethod @Parameters @Optional @Listeners
@Parameters({ "browser", "url", "headless" }) @BeforeMethod(alwaysRun = true) public void setUp( @Optional("chrome") String browser, @Optional("amazon") String urlKey, @Optional("false") String headless) { DriverFactory.createDriver(browser, ...); openUrl(urlKey); // looks up URL from properties }
base/ConfigReader.java
Config Loader
"Think of it as a phone book — you look up a name (key) and get back a number (value like a URL or locator)."

What it does: Reads url.properties and or.properties files from disk once at startup. After that any part of the code can call ConfigReader.url("amazon") and get https://www.amazon.in back.

Where it starts: Static initializer block — loads files when the class is first referenced.

Where it ends: url(key), locator(key), browser(key) methods — simple lookups, nothing complex.

url.properties or.properties static init block
base/ExtentManager.java
Report Manager
"Think of it as a shared test-result notebook — all threads write into it but each gets their own separate page so entries don't mix."

What it does: Creates and manages the Extent HTML report. Because multiple threads are running tests at the same time, it uses ThreadLocal again — each thread has its own "test node" so log entries never appear in the wrong test.

Where it starts: init() — creates the single ExtentReports object. Called from BaseClass @BeforeSuite.

Where it ends: flush() — writes the HTML file to disk. Called by SuiteListener once all threads are done.

ExtentReports ExtentSparkReporter ThreadLocal<ExtentTest> double-checked locking
listeners/TestListener.java
Auto-Reporter
"Think of it as a security camera — it watches every test automatically, and takes a screenshot the moment anything fails."

What it does: TestNG calls this automatically at key moments — when a test starts, when it passes, when it fails, when it's skipped. You don't call it yourself. On failure it takes a browser screenshot and embeds it into the HTML report.

Key methods:

onTestStart → logs START onTestSuccess → logs PASS onTestFailure → screenshot + logs FAIL onTestSkipped → logs SKIP
listeners/SuiteListener.java
Report Finalizer
"Think of it as the printer button — it waits until every test is done, then prints the report exactly once."

What it does: Has exactly one method: onFinish(ISuite). TestNG calls it after every thread is done. It calls ExtentManager.flush() to write the final HTML report to Report/htmlReport.html.

Why not just use @AfterSuite? Because @AfterSuite runs on a test thread, and at that point other threads might still be finishing. SuiteListener.onFinish() is guaranteed to run after all threads are completely done.

tests/AmazonSearchTest.java
@Parameter Demo
"A real test — it tells a browser to go to Amazon, pick a category, search for a product, and confirm results appeared."

Where it starts: The @Test searchProduct() method receives a category and searchTerm from the XML (e.g., "Books" and "Harry Potter") as parameters. It uses these to drive the browser.

Where it ends: After asserting that search results appeared on the page.

@Parameters({ "category", "searchTerm" }) @Test public void searchProduct( @Optional("Books") String category, @Optional("Harry Potter") String searchTerm) { // select category from dropdown // type searchTerm into search box // click search button // assert results appeared }
tests/ParallelMethodsTest.java
parallel="methods" demo
"Four people each checking a different thing on the same website at exactly the same time."

What it does: Contains 4 @Test methods: searchBox, categoryDropdown, searchButton, pageTitle. When run with parallel="methods", TestNG runs all 4 at the same time — each in its own browser.

Where it starts/ends: Each method is independent. They all start within milliseconds of each other.

tests/ParallelInstancesTest.java
@Factory + parallel="instances"
"The same test person cloned 3 times — each clone visits a different website simultaneously."

What @Factory does: Returns multiple instances of the test class, each configured differently (amazon, bbc, facebook). TestNG creates 3 separate objects and runs them in parallel.

@Factory public static Object[] createInstances() { return new Object[] { new ParallelInstancesTest("amazon"), new ParallelInstancesTest("bbc"), new ParallelInstancesTest("facebook"), }; }
tests/DataProviderParallelTest.java
@DataProvider(parallel=true)
"One recipe, three ovens — the same test runs 3 times simultaneously with different ingredients (data rows)."

What it does: Uses @DataProvider(parallel=true) — one method, three data rows. TestNG runs all 3 at the same time. A data provider is just a method that returns a 2D array of values; TestNG feeds each row to the test.

{ "Books", "Harry Potter" } { "Electronics", "Bluetooth" } { "Computers & Accessories", "Keyboard" }
dataproviders/SearchDataProvider.java
Data Supplier
"Think of it as a spreadsheet — it supplies rows of data to the test, which runs once per row."

What it does: Contains three @DataProvider methods. searchTermsParallel() returns 3 rows and is marked parallel=true — so all 3 rows run at the same time. searchTerms() is the serial version.

05 — @Parameters & @Optional
How values flow from XML to code
Understanding the priority chain
Source 1 (Highest Priority)
Command Line
-Dbrowser=firefox overrides everything. Used in CI pipelines.
Source 2
XML <parameter>
Values inside testng.xml or suite files. Normal way to pass data.
Source 3 (Lowest Priority)
@Optional("default")
Fallback value when the XML doesn't supply the parameter at all.

@Optional explained

Without @Optional, if the XML doesn't supply a <parameter name="browser">, TestNG throws an error and the test fails to start.

With @Optional("chrome"), if the XML is silent about "browser", the method just gets the string "chrome" instead — no error, test runs normally.

// XML supplies "browser" → uses "edge" // XML doesn't supply "browser" → uses "chrome" (the @Optional default) public void setUp(@Optional("chrome") String browser) { … }
📋

Example from parameters-demo.xml:
Test "AllParametersSupplied" passes browser=edge in XML → setUp gets "edge".
Test "OptionalDefaultsUsed" passes nothing → setUp gets "chrome" (from @Optional).
Test "TestLevelOverridesSuiteLevel" passes browser at test-level → overrides the suite-level parameter.

06 — Parallel Modes
5 ways to run tests at the same time
Each mode answers a different question: "what is the unit that runs in parallel?"
Mode 1

parallel="tests"

Each <test> block in the XML runs in its own thread. All methods inside one <test> still run one at a time.

Used in: testng.xml (Chrome vs Edge cross-browser)

parallel="tests" thread-count="3"
Mode 2

parallel="methods"

Every @Test method runs in its own thread. If a class has 4 methods, all 4 browsers open simultaneously.

Used in: parallel-methods.xml (ParallelMethodsTest — 4 methods)

parallel="methods" thread-count="4"
Mode 3

parallel="classes"

Each test class runs in its own thread. All methods in one class run sequentially (one at a time), but different classes run together.

Used in: parallel-classes.xml (3 test classes)

parallel="classes" thread-count="3"
Mode 4

parallel="instances"

Each object instance of a class runs in its own thread. Requires @Factory to create multiple instances.

Used in: parallel-instances.xml (@Factory returns 3 instances: amazon, bbc, facebook)

parallel="instances" thread-count="3"
Mode 5

@DataProvider(parallel=true)

Each data row gets its own thread. No parallel= in XML — the parallelism is declared on the data provider method itself.

Used in: parallel-dataprovider.xml (3 rows × 1 method = 3 simultaneous browsers)

data-provider-thread-count="3"
🔒

Why ThreadLocal is the key to all of this: Without it, Thread A might accidentally use Thread B's browser. ThreadLocal gives every thread a private storage slot — like a numbered locker. So when Thread A calls DriverFactory.getDriver(), it always gets its own browser, never Thread B's. This is what makes all 5 parallel modes safe.

▶️

How to run: mvn test -DsuiteXmlFile=suites/parallel-methods.xml — change the XML file name to try each mode. Run suites/regression-all.xml to execute all 34 tests at once.
