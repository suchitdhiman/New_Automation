01What this project is

Think of it as a textbook you can run.

Most TestNG tutorials show you a snippet, you nod, and a week later you cannot remember whether @BeforeTest runs once per class or once per something else. This project answers those questions by executing them. The lifecycle test does not describe the order TestNG calls your annotations in - it records the order as it happens and then asserts on it. If a future TestNG version changes that order, the test goes red and tells you.

Underneath the teaching, it is a genuine automation framework: page objects, a thread-safe driver factory, environment config, retries, Excel-driven data, screenshots on failure, and its own reports. Nothing here is a toy that would fall over on a real project.

The two halves

Roughly half the test classes never open a browser. They are about TestNG mechanics - invocation counts, thread pools, dependency graphs, assertion styles. Starting a Chrome instance for those would add thirty seconds to the run and prove nothing, so they extend BaseTest.

The other half drive the actual application and extend BaseWebTest, which handles the browser for them. That split is why mvn test finishes in seconds for the concept suites and takes a minute for the full regression.

02The website we drive

Swag Labs at https://www.saucedemo.com - a small online store selling branded merchandise. Sign in, browse six products, sort them, add to a cart, fill in shipping details, see the totals, place the order. A complete e-commerce journey in about six clicks, which is exactly the right size for teaching.

It was built for automation practice, so it is stable, it is always up, and nobody minds you hammering it. Better still, it ships four different accounts that behave differently on purpose - which is what gives this project real material for negative tests, retries and timeouts instead of made-up examples.

The password is secret_sauce for all of them. The site publishes these on its own login page, so there is nothing secret here - but they still live in config.properties rather than being hard-coded, because that is the habit you want when the same framework points at a real environment.

03How it all fits together

Six things happen in a line, and a set of listeners watches all of it from the side. That is the whole architecture.

The one decision everything rests on

DriverFactory holds the browser in a ThreadLocal - a variable where every thread gets its own private copy. When a suite says "run four tests at once", four threads each get their own browser, and no page object has to know that parallelism exists.

That single decision is what lets any suite in this project switch between parallel modes without touching one line of test code.

04Life of one test

This is the diagram to keep. Everything TestNG does, in the order it does it, for a single test method. The indentation is the point: each @Before has a matching @After, and the inner ones run more often than the outer ones.

The one people get wrong

@BeforeTest has nothing to do with a test method. It is about the <test> tag in your suite XML. If your XML has three <test> blocks, it runs three times. @BeforeMethod is the one that runs before every test method.

The two base classes

BaseTest gives you a logger and class-level logging. That is all. Extend it when your test does not need a browser.

BaseWebTest extends BaseTest adds the browser: it starts a fresh driver before every test method and quits it afterwards, and hands you loginPage() to begin a journey. Extend it when your test drives the application.

06The eleven concepts

Numbered to match the suite files, so concept 3 is suites/03-*.xml. Each one is a sentence about what it is, a sentence about why you would reach for it, and the exact command to watch it run.

1   Annotations, and the order they fire in

What it is. The ten @Before and @After hooks that wrap your tests, plus the attributes you can put on @Test itself - priority, enabled, timeOut, expectedExceptions, description.

Why you care. Put setup at the wrong level and you either repeat expensive work on every test, or you share state between tests that should be independent. Knowing which hook runs how often is the difference.

One attribute worth singling out: enabled = false does not report a skip - the test vanishes from the report entirely, and six months later nobody remembers it existed. Prefer a SkipException with a reason.

Code
tests/annotations/AnnotationLifecycleTest, TestAttributesTest
Run
mvn test -DsuiteXmlFile=suites/01-annotations-and-attributes.xml

2   Suite properties, applied to classes from the XML

What it is. <parameter> declared in the suite XML and injected into your code with @Parameters. It can be declared at suite level, at <test> level, and at <class> level - and the most specific one wins.

Why you care. It is how one test class runs against three browsers or four environments without an if statement anywhere in it.

This suite declares the same parameter at all three levels at once so you can see the override chain in a single file. It also proves a distinction that catches people out: @Parameters injection can see a class-level parameter, but ITestContext.getCurrentXmlTest().getParameter() cannot - a test context covers a whole <test> block, and a class-level value is not defined at that scope.

Code
tests/suiteconfig/SuiteParameterTest
Run
mvn test -DsuiteXmlFile=suites/02-suite-parameters.xml

3   Parallel execution, at five different levels

What it is. TestNG can hand out threads by method, by class, by <test> block, by factory instance, or by whole suite. They are not interchangeable - each one decides what unit of work gets its own thread.

Why you care. A one-hour regression becomes ten minutes. The cost is that your tests have to be genuinely independent - which is a discipline worth having anyway.

Code
tests/parallel/ - five classes
Run
suites/03-parallel-methods.xml, -classes, -tests, -instances, and suites/13-suite-of-suites.xml

4   Groups, and filtering on them

What it is. Tag a test with groups = {"smoke", "cart"}, then have the suite XML include or exclude those tags.

Why you care. One codebase, many pipelines. Per-commit runs smoke. Nightly runs regression minus flaky. A release gate runs a <define>d group made of other groups.

Two rules that settle arguments: exclude always beats include, and a method can be in several groups at once. Tag by speed (smoke, regression) and by area (cart, checkout) and you can slice either way.

Code
tests/groups/GroupedCatalogTest
Run
mvn test -DsuiteXmlFile=suites/04-groups-and-filters.xml -Dheadless=true

5   Dependencies, invocation counts and thread pools

What it is. dependsOnMethods and dependsOnGroups say "do not bother running me if that failed". invocationCount runs the same method N times, threadPoolSize spreads those runs over threads, and successPercentage lets some of them fail.

And the question everyone eventually asks: can thread-count be negative? No. The XML model will happily store -4, because XmlSuite is a plain bean that does not validate. But TestNG builds a fixed thread pool from that number, and a fixed pool rejects anything below 1. So a negative thread-count is a configuration bug that surfaces at run time, not a clever way of saying "unlimited". ThreadCountBoundaryTest asserts both halves of that.

Code
tests/dependency/, tests/execution/
Run
mvn test -DsuiteXmlFile=suites/05-dependency-invocation-threads.xml -Dheadless=true

6   Hard and soft assertions

What it is. A hard assertion (Assert.assertEquals) throws the moment it fails, so nothing after it runs. A soft assertion (SoftAssert) records the failure and carries on, reporting everything at assertAll().

Why you care. Use hard when everything downstream depends on the check - there is no sense verifying cart totals if login did not work. Use soft for independent observations about one screen, so one run tells you all four things that are wrong instead of the first one, four times, over four afternoons.

Two traps, both handled in the code. Forgetting assertAll() makes the test pass silently - the single most common way a suite ends up green and worthless. And sharing one SoftAssert across threads mixes failures from every parallel test together, which is why ours lives in a ThreadLocal.

Code
tests/assertions/HardAssertionTest, SoftAssertionTest
Run
mvn test -DsuiteXmlFile=suites/06-assertions.xml -Dheadless=true

7   Listeners, all nine of them

What it is. Hooks that let you observe or change the run without touching a test. This project implements every listener interface TestNG offers.

InterfaceFiresWhat ours does
IExecutionListenerOnce per JVM runCreates output folders, resets counters
IAnnotationTransformerPer @Test, at load timeAttaches retries to @Flaky methods
ISuiteListenerAround each suitePrints the parallel mode and thread count banner
ITestListenerPer test resultDecides pass / fail / skip, writes the ledger
IInvokedMethodListenerAround every methodTakes the failure screenshot
IConfigurationListener@Before/@After resultsNames the setup method that broke
IMethodInterceptorOnce, before anything runsPulls smoke tests to the front
IRetryAnalyzerAfter a failureDecides whether to re-run
IReporterOnce, at the endConsole block, HTML, Excel

There are three ways to register one, and the project uses all three so you can compare: the service loader file (META-INF/services/org.testng.ITestNGListener) applies to every suite; <listeners> in a suite XML applies to that one suite; @Listeners on a class applies to the whole <test> block containing that class.

Measured, not assumed

@Listeners does not scope to the annotated class, which is what almost everyone expects. Running testng.xml, the listener declared on one class observed all five classes in its <test> block and none in the other block. If you want per-class behaviour, the listener has to filter for itself.

Run
mvn test -DsuiteXmlFile=suites/07-listeners.xml (no browser, ~2s)

8   Data providers and retries

What it is. A @DataProvider feeds the same test method many rows of data; each row becomes its own result. A retry analyzer re-runs a failed test a bounded number of times.

The project shows four provider shapes: a plain Object[][]; a lazy Iterator; one that inspects the Method it is feeding and changes what it returns; and one that reads the ITestContext so a smoke run gets fewer rows than a regression run.

The rule on retries. They are for genuine environmental noise, not for making a broken test green. That is why ours only attaches to methods marked @Flaky, and why that annotation asks for a reason and a ticket number.

Code
dataproviders/, tests/retry/, listeners/RetryAnalyzer
Run
mvn test -DsuiteXmlFile=suites/08-dataproviders-and-retry.xml -Dheadless=true

11   The Page Object Model

What it is. Every locator, wait and click lives in a page class. Tests only describe intent.

// The whole purchase journey. No locator, no wait, no findElement.
CheckoutOverviewPage overview = loginPage().loginAs(TestUser.STANDARD)
        .sortBy(SortOption.PRICE_LOW_TO_HIGH)
        .addToCart(BACKPACK)
        .addToCart(BOLT_TSHIRT)
        .openCart()
        .checkout()
        .enterShippingDetails("Ayush", "Dhiman", "560037")
        .continueToOverview();

Why it works. Four rules, followed everywhere in com.sk.pages:

  • A page action returns the page you land on. cart.checkout() gives you a CheckoutInformationPage, so the compiler stops you calling a checkout method while you are still on the cart.
  • Page objects assert nothing. They expose state; the test decides what is correct. A page that asserts cannot be reused by a test with different expectations.
  • Page objects return real types. double for a price, not the string "Total: $32.39". Parsing is the page object's job.
  • No Thread.sleep anywhere. Every wait is an explicit condition in BasePage.
Code
pages/ - seven classes. tests/e2e/EndToEndPurchaseTest
Run
mvn test -DsuiteXmlFile=suites/11-pom-end-to-end.xml -Dheadless=true

07Things to try

In rough order of how much they teach. Run them from the project root. In Eclipse, right-click any suite XML and choose Run As → TestNG Suite instead.

01See all three statuses in one run

The fastest way to understand the reporting. This suite is designed to end red.

mvn test -DsuiteXmlFile=suites/10-skip-and-status-showcase.xml -Dheadless=true
What to look for The summary block at the end of the output, then open test-output/custom-report/execution-summary.html and test-output/screenshots/. Exactly two screenshots, because only two of the failures involved a browser.

02Watch four browsers work at once

Drop -Dheadless and the browsers become visible. Four windows, four tests, one class.

mvn test -DsuiteXmlFile=suites/03-parallel-methods.xml
What to look for In the log, the [TestNG-methods-1] column. The method names interleave - that is parallelism, not four tests taking turns.

03Prove parallelism is actually saving you time

Run the same suite twice, once sequentially. Edit thread-count in suites/03-parallel-methods.xml from 4 to 1 and compare Time elapsed.

mvn test -DsuiteXmlFile=suites/03-parallel-methods.xml -Dheadless=true
What to look for Roughly four times the wall clock at thread-count="1", while Total runtime ... of test-method time in the summary stays about the same. That gap is the whole point.

04Break a test on purpose

In tests/parallel/ParallelMethodsTest, change the expected product count from 6 to 5 and run it.

mvn test -DsuiteXmlFile=suites/03-parallel-methods.xml -Dheadless=true
What to look for A PNG appears in test-output/screenshots/ named after the method, the failure row turns red in the HTML report, and the console summary lists it under Not-passed detail. That is the listener chain doing its job. Change it back afterwards.

05Add a test case without writing Java

Open src/test/resources/testdata/SwagLabsTestData.xlsx, go to the LoginData sheet, and add a row: TC-E10, username problem_user, password wrong, ShouldLogin N, ExpectedMessage Epic sadface: Username and password do not match any user in this service, Execute Y. Save.

mvn test -DsuiteXmlFile=suites/09-excel-driven.xml -Dheadless=true
What to look for One more row in the results, labelled TC-E10. Then set Execute to N and watch it disappear. Also try renaming a column header to see the loud, helpful failure.

06Slice the same tests four different ways

One class, four <test> blocks, four different group filters. Nothing in the Java changes.

mvn test -DsuiteXmlFile=suites/04-groups-and-filters.xml -Dheadless=true
What to look for Each block reports a different count. Then open the XML and add <exclude name="cart"/> to the smoke block and watch one test drop out.

07Watch a retry happen

FlakyRetryTest fails deliberately on its first attempts and passes on a later one.

mvn test -DsuiteXmlFile=suites/08-dataproviders-and-retry.xml -Dheadless=true
What to look for RETRY 1/2 and RETRY 2/3 lines in the log, followed by ATTEMPT DISCARDED. Then compare surefire's Skipped: 3 against our summary's SKIPPED: 0 - both are describing the same run, and ours is counting the way a human would.

08Run Chrome and Edge side by side

Two <test> blocks, two browser parameters, one thread each.

mvn test -DsuiteXmlFile=suites/12-cross-browser.xml -Dheadless=true
What to look for Started CHROME and Started EDGE in the log. Now run it again with -Dbrowser=chrome added and watch both blocks start Chrome - a system property beats the XML parameter, which is trap 1 below.

09Switch environment

config/staging.properties layers on top of config.properties - longer waits, an extra retry, headless on by default.

mvn test -DsuiteXmlFile=suites/07-listeners.xml -Denv=staging
What to look for The suite banner at the top of the log now says Environment : staging, and the configured wait has changed from 15s to 25s.

10Run everything

Six blocks, four parallel modes, the full 147 tests.

mvn test -DsuiteXmlFile=suites/master-regression.xml -Dheadless=true
What to look for About 83 seconds of wall clock against roughly 215 seconds of test-method time. One deliberate skip. Zero failures.

Why two numbers disagree

Surefire and the custom summary sometimes report different totals, and the custom one is right. TestNG marks an attempt discarded by a retry analyzer as skipped, so a test that failed twice and passed on the third go shows up in surefire as "1 passed, 2 skipped". Our listener filters those out.

09Four traps we hit

These were not found by reading documentation. They were found by running the suites and watching them fail in confusing ways. Each is fixed and commented in the code where it was fixed - and each one is the kind of thing that costs an afternoon on a real project.

1. A command-line flag silently beat the cross-browser suite

Symptom: green build, and the <test name="Edge"> block was running Chrome.

Cause: for @Parameters injection, TestNG gives a matching system property priority over the XML. The pom was forwarding browser in surefire's <systemPropertyVariables>, so every block got Chrome regardless of what the XML said. Nothing failed. The coverage was simply not there.

Fix: stop forwarding it. -Dbrowser=edge still works as a deliberate override.

2. A page object in a field is shared between threads

Symptom: NoSuchSessionException: Session ID is null, RejectedExecutionException ... [Shutting down], random StaleElementReferenceException. None of them point at the cause.

Cause: TestNG creates one instance of a test class and runs every method on it. Under parallel="methods" - and far more aggressively with a parallel data provider - several threads share that instance. A loginPage field assigned in @BeforeMethod was being overwritten by one thread while another was using it, and then that thread quit the browser.

Fix: loginPage() is a method, not a field. It builds a page object from the ThreadLocal driver every time it is called. The rule that falls out of this: in a parallel suite, a test class must hold no mutable instance state.

3. React drops keystrokes under parallel load

Symptom: intermittent "username and password do not match", on standard_user, with correct credentials. Different tests each run. Impossible to reproduce by hand.

Cause: Swag Labs uses React controlled inputs. With three headless Chromes competing for CPU, the onChange handler falls behind and characters get dropped - sendKeys("standard_user") leaves standard_use in the field. It looks exactly like a product bug.

Fix: BasePage.type() reads the value back with getDomProperty("value") and retypes if it does not match. Fixing it in one place means no test and no page object has to know about it.

4. Two libraries disagreed about logging

Symptom: NoSuchFieldError: DefaultFlowMessageFactory ... INSTANCE before a single test ran.

Cause: Apache POI pulls in older log4j-api and slf4j-api versions than Selenium and log4j-core need. Maven resolves conflicts by "nearest definition wins", so the older ones won.

Fix: a <dependencyManagement> block, which beats transitive resolution at any depth. Whenever a build dies with NoSuchMethodError or NoSuchFieldError inside a library you never called directly, run mvn dependency:tree and look for exactly this.

Nothing to install

Selenium 4.6 and later ship Selenium Manager, which downloads the matching driver binary by itself. There is no WebDriverManager dependency and no chromedriver.exe to keep in step with your browser version.
